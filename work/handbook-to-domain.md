# 从创始人手册到领域手册

把创始人手册里属于某领域的规范迁入该领域手册。2026-10 首次实例：创始人手册 `work/human-agent-collaboration.md` 迁入知识工作手册 `stage/clarify.md`，原文的「人机协作」被重新定义为生命周期阶段「澄清」。

本篇由这一次操作反推。只有一个实例，仍是案例草稿，不作标准。

## 做法

1. 筛候选：按标题与正文判断文档属于哪个领域，不看它现在住在哪个目录。本例「人机协作」归知识工作。
2. 定性质：确认它是手册（规范），不是日志、洞察、文集。目标仍是手册，资产类型不变。
3. 定落点：读目标手册的目录体系，按内容找落点。本例目标手册只有 `piece/`、`process/`、`place/`，没有对应维度，新开 `stage/`；目录名由创始人定。
4. 改体例：按目标手册的写法重写。本例从散文三节改为「定义 / 生命周期 / 验收」，术语从「AI」改为「智能体」，标题从「人机协作」改为「澄清」。
5. 写目标：在目标子仓库写就，同步 `index.md` 与 `CHANGELOG.md`，提交推送。
6. 删源：源侧删文，同步 `index.md`、`myst.yml`、`README.md`、`CHANGELOG.md`，提交推送。
7. 断链：删掉源侧指向该文的目录项与导航项，不补跨仓库相对链接。
8. 指针：目标侧 handbook → 领域仓库 → 根仓库；源侧 handbook → 创始人仓库 → 根仓库。
9. 复核：两边工作区干净，目标索引收录、源索引已无此文件；git 历史即移动凭证。

## 与「从主体到领域」的差异

- 多一步改体例：手册是规范，迁入不是原文搬家，要按目标手册的三段式重写。
- 落点不能只看资产类别：还要看目标手册内部的目录维度。源侧的 `work/` 在目标侧可能不存在，需要按目标体系重判，甚至新开目录。
- 内容可能被重新定义：本例不只是换位置，而是把「人机协作」重定义为阶段「澄清」。
