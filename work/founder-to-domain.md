# 从创始人仓库到领域仓库

把创始人名下某个资产仓库里属于某领域的内容，迁入该领域第二大脑的对应仓库。可迁的不只是手册：日志、档案、意图、洞察、路线图、报告、参考、归档、章程、手册、规范、教程、文集、画廊、宣传册、历史、语境，都走同一套做法。

2026-10 首次实例：创始人手册 `work/human-agent-collaboration.md` 迁入知识工作手册 `stage/clarify.md`，原文的「人机协作」被重新定义为生命周期阶段「澄清」。

本篇由这一次操作反推。只有一个实例，仍是案例草稿，不作标准。

## 做法

1. 筛候选：按标题与正文判断内容属于哪个领域，不看它现在住在创始人哪个仓库。
2. 定性质：确认它属于哪件资产，判据是它讲什么、按什么格式维护——日志按日期、档案按材料、洞察按陈述式条目、手册按三段式规范、文集是散文。不要按它现在住的目录定性质。
3. 定落点：在目标领域找同名资产仓库，按内容定具体位置。目标侧通常与源侧同构；找不到对应目录时，按目标仓库的目录体系重判，必要时新开目录，命名由创始人定。
4. 改体例：按目标资产的写法重写。每种资产有自己的体例——手册是「定义 / 生命周期 / 验收」，日志按日期成文件，档案按材料分类，洞察按陈述式条目，文集是散文。术语、标题、文件名随目标侧。
5. 写目标：在目标子仓库写就，同步该仓库的 `index.md` 与 `CHANGELOG.md`，提交推送。
6. 删源：源侧删文，同步源仓库的 `index.md`、`myst.yml`、`README.md`、`CHANGELOG.md`，提交推送。
7. 断链：删掉源侧指向该内容的目录项与导航项，不补跨仓库相对链接。
8. 指针：目标侧 资产子仓库 → 领域仓库 → 根仓库；源侧 资产子仓库 → 创始人仓库 → 根仓库。
9. 复核：两边工作区干净，目标索引收录、源索引已无此内容；git 历史即移动凭证。

## 与「从主体到领域」的差异

- 多一步改体例：迁入不是原文搬家，要按目标资产的体例重写；手册只是其中一种。
- 落点不能只看资产类别：还要看目标仓库内部的目录维度。源侧的目录在目标侧可能不存在，需要按目标体系重判，甚至新开目录。
- 内容可能被重新定义：本例把「人机协作」重定义为阶段「澄清」；其他资产同理，迁入时按目标资产的关注点重组。
