# 后台实现任务的派单

## 场景

个人小程序需要一个后端来收集信息。接口分两类：按需要定制的接口，以及可复用的通用接口。两类接口先要落成可运行的服务。

这一轮不自己写，也不把实现留在当前对话里，而是交给后台 agent 跑。前台是 Hermes，执行者是 Pi。

## 派单

原话：

> To hermes： 给 pi 发一个后台任务实现这两个 API，包括代码、测试、用户文档、开发文档，确保测试和文档覆盖率。

拆成四项：

- 对象：Pi 是执行者，Hermes 只负责转发与回收。
- 任务：实现两个 API，边界清楚，可独立验收。
- 交付：代码、测试、用户文档、开发文档，缺一件不算完成。
- 合格线：测试与文档覆盖率。

## 为什么这样派

把「实现」定义成四件套，而不是「把代码写出来」。后台 agent 最容易只交代码；测试与文档如果不在派单里，通常不会自己长出来。

把覆盖率写进任务，等于把「做完」从主观判断变成可检查的交付。覆盖率不必是一个精确阈值，但必须在派单时说清楚，否则执行者只能猜。

把任务放到后台，适合这种边界清楚、不需要人逐步决策的实现工作。当前对话继续处理别的事，Pi 在后台跑完再回收。

协调者与执行者分开，派单语言可以很短。Hermes 不需要理解实现细节，只需要把上下文、交付物与合格线完整转给 Pi。

## 缺口

这次派单有四处没有写死，值得下次补上：

- 「这两个 API」没有在派单里展开。Pi 如果不在同一上下文里，必须先拿到接口契约，否则只能猜。
- 覆盖率没有阈值，也没有指定测试命令与文档位置。
- 没有写清分支、提交方式、产物路径与失败回传方式。
- 没有留下实现结果与验收记录，本判例只到派单，不到复盘。

## 可复用的派单模板

给后台 agent 派实现任务时，至少写清五件事：

1. 上下文：仓库、分支、接口契约或规格在哪。
2. 交付：代码、测试、用户文档、开发文档，逐项列出。
3. 合格线：测试命令、覆盖率阈值、文档位置。
4. 回传：分支名、提交要求、产物路径、失败时怎么报。
5. 验收人：谁看结果、按什么判。

## 复盘

这个判例的价值不在两个 API 的内容，而在派单结构：短指令也能把一件事说完整，前提是对象、交付、合格线三件事不缺。缺了它们，后台 agent 跑得越快，返工越大。

下一步可以把这条派单写成一份任务蓝图：输入是接口契约与仓库，步骤是实现、测试、文档，判据是测试通过、覆盖率达标、文档齐全，偏差是接口契约缺失或测试环境不可用。这样同一个派单可以重复用，不必每次重写。
