# 协作纪律

从失败里长出来的操作纪律，不是技术坑。

- 并行工具调用对同一路径又写又删 → 竞态，后一个调用会删掉前一个刚写的文件。同一路径的写、删、移动必须串行。
- 目录搬迁收尾三件事：内部相对链接按新位置重算、全仓 grep 旧路径（README 目录树、CHANGELOG、别的仓的引用）、`grep .gitignore` 里的路径锚点（否则生成物被误提交）。
- 重写已有文件前先读现文件 → 两轮之间可能已有新提交，直接 `write` 会覆盖。
- 落点先看本域有没有专用子模块 → 按别的领域的先例推断落点会写错地方（已建却闲置的 `data/insight/` 就是反例）。
- 交付一个「应该被用」的工具前，先验证它自己被目标场景用过一次 → 只在测试与示例里跑过的 CLI 等于没跑。
- 报数类交付前按解析器口径实数 → 估数会错（曾把 19 条报成 18 条，漏了首行那条）。
- 实验先修幂等再测数，且先自问「答案我事先知不知道」——预期已知的验证不算实验（判据在 `product.md` 的验收与实验一节）。
- 官方文档与实现不符时以实测为准：装配置类任务里文档写的语法可能被 schema 拒（OneBase 的 `struct` 字段就是），完善资料时把文档错误一并指出，不照抄。
- 指令里两处路径互为倒序（「整理到 `intro/metaphysics/`」与「提交到 `metaphysics/intro/`」）→ 按字面各建一个、不替用户合并，做完显式报告这处冲突。
- 用户连续重复粘贴同一段内容（同一条 skill 定义连发两次）→ 按一次处理，不追问。
- AI 草稿的对话残留：开头「好，我们开始」「好，直接进 Unit 2」、结尾「如果你愿意，我可以…」这类对用户说话的语气，发布前一律删。
- 文档里不代拟未定义的内容：规则还没定义就写「规则清单」等于编，宁可留着不写；把流程图里的框当命令名、把存储名词当命令，都是同一种病。
- 脱敏复查不能只 grep 全名：单字姓名关键字（「搜『玲』」这类）同样指向真人，复查项要含全名、单字、邮箱、域名、本机路径、群/表 ID。
