# qtfounder 给 qtcloud 探路

2026-10-28 定位决策：`qtfounder`（探路仓，创始人的驾驶舱与规则工厂）与 `qtcloud`（产品仓，量潮云的门户与工作台）两仓并列存在，成果单向分岔——探路在前者，毕业进后者，不回流。

## 判例

现象：两个仓各有 `site`、`studio`、`provider`、`cli`，模块重名；探路仓的 STATUS 还停在 2026-08-23 的「官网 + 工作台」，两仓关系没有写下来。

错法：把两付认成同一产品的两个版本，于是要么考虑并列维护两套，要么想在探路仓上直接加团队功能。

正法：分岔。产品唯一的归宿是产品仓。探路仓收敛为驾驶舱加规则工厂，它的四个应用模块——官网、工作台、服务端与 lite 原型——划为探路区。探路区为产品仓试手感、试数据模型，随时推倒重写。

## 理由

事实：产品仓的 AGENTS.md 立了十二条交互原则，来自 `examples/studio` 的两版原型：v1 六卡平铺，v2 自评 3 分。那次毕业的是原则与案例，不是那版代码，这就是本模式的样板。

规则层已完成个人到组织的迁移——《量潮科技文档格式章程》以公司名义立，署名有 `type: org` 与四个法人全名，禁用词清单按期治理；产品层还没有。运维通道（`qtcloud-devops` 与 terraform 清单）也已在产品仓一侧。

判断：两仓的信任边界不同。探路仓跑在 owner 即管理员的世界，产品仓接团队就必须有成员、角色与离职回收，这是另一套骨架，不是加功能能长出来的。而探路仓值钱的部分不依赖界面，是随二进制发布的契约、检查器与 Skill。探路区的不稳定若与主线区混在同一个版本承诺里，别人就没法判断这个仓哪些能依赖。

不做两套产品并列维护：团队功能一旦开始，「owner 即管理员、数据源指向本仓子模块」这两处硬编码立刻变成维护负担，而它们在探路期正是便利。

## 三类不稳定

| **类型** | **探路期** | **毕业时** |
|:--|:--|:--|
| 手感 | 随便试，这是探路的本职 | 毕业的是新增的原则与案例存照 |
| 数据模型 | 允许硬编码创始人与本仓子模块，每改一次模型记一句为什么改 | 硬编码换成成员、角色与外部数据源 |
| 技术栈 | 换库换框架都在这里烧掉 | 不毕业 |

代码大概率不毕业，毕业的是验收标准、数据模型与案例。

## 毕业标准

1. 模型稳了：数据结构连续若干次迭代不改名，每个字段说得清为什么存在；
2. 换掉硬编码：「owner 即管理员」与「数据源指本仓子模块」这两处，毕业前换成成员、角色与外部数据源；
3. 对得上原则：能逐条对上产品仓的十二条交互原则；对不上就改实现，或把新原则写进它的 AGENTS.md——写进去即升级为全仓约束，慎开这个口子；
4. 有人用过不骂：哪怕那个人只是创始人，连续用几周不别扭。v2 自评 3 分那种不毕业。

反向信号：产品仓的东西被拷回探路仓，说明毕业判断错了，该修的是判断，不是继续搬代码。

## 新功能落哪

问三句：为谁做的？用谁的数据？谁改它的规则？三句里出现第二个人，进产品仓；都是创始人自己，留探路仓。

## 待办

决策已定，仓内文档未动：探路仓的 README 与 STATUS 要按主线区、探路区重写，AGENTS.md 补两区边界声明；产品仓的 AGENTS.md 要补接收流程，写清毕业标准与反向信号。落地之前，这条决策只活在本文里。
